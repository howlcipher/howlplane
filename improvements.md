# 🚀 Improvement Backlog

This document is the authoritative, ranked backlog for the AI Knowledge Library. It is designed so a fresh session (Claude Code or Gemini CLI) can pick up the next item with zero prior chat context.

## Working Protocol

This protocol applies to every worked task — backlog improvements and bug fixes alike. Bugs are tracked in `issues.md`, which mirrors this file's format and shares this protocol; a hotfix without a backlog row still gets steps 1 through 4 and 7.

1. **Open a task journal.** Copy `documentation/task_journals/TEMPLATE.md` to `documentation/task_journals/YYYY-MM-DD_<slug>.md`. The journal is the resume point after a session limit or power outage: update it and commit at every milestone, and always keep its "Next step" line current so a fresh session can continue from the journal alone. It is a resume artifact, not permanent documentation — it gets deleted in step 7, so anything durable (findings, decisions, verification evidence) must land in the item's Done note, the changelog, or a proper doc before the task closes.
2. **Re-evaluate the model (every run, before starting).** The table's model columns are starting suggestions, not commitments. Check what is actually available right now — currently: Claude Pro subscription (Claude Code), Google subscription via Antigravity CLI (`agy models` lists live names; quota is per model), and local Ollama (`curl localhost:11434/api/tags` — models change). Update this sentence if subscriptions or tools change. Pick the least expensive available model that can do the job well and escalate only if the task proves harder than expected. To preserve Claude session limits, the default is to orchestrate from Claude Code but delegate implementation to a non-Claude model headlessly (`agy -p "<brief>" --model "<model>" --mode accept-edits`) per the delegation policy in `.agents/prompts/work_next_item.md`; Claude Code subagents bill the same Claude plan and do not save limits. Record the choice and one line of reasoning in the journal. Consult `documentation/model_tool_roster.md` for the maintained model roster and known delegation lessons before re-evaluating from scratch each time.
3. **Route the crafted skills.** Check the skills manifest (`.agents/skills.json` or the AGENTS.md table) for skills matching the task and read the matching SKILL.md files before planning. Honor tier precedence and the Related Skills deferrals.
4. **Scan for helpful free tools.** Briefly consider whether a free or open source tool (a CLI already installed, a linter, a library, an MCP server) would materially improve the work. Record recommendations in the journal; use tools that are already available freely, and ask before installing anything new. Check `documentation/model_tool_roster.md`'s Discovery sources section (There's An AI For That, the MCP server registry, package indexes) when nothing already available fits.
5. **Read the detail section** for the item (linked from the table) plus any referenced docs before coding. Background docs: `documentation/multi_agent_payload_protocol.md` and ADR 0003.
6. **Constraints:** this machine has no Anthropic or Gemini API keys; live LLM pipeline runs go through local Ollama.
7. **Finish the loop:** every code change ships with relevant automated tests in the same task — add or update tests covering the new behavior's success and failure paths (see `quality_assurance` for design standards). Use `make test-changed` or `make test-fast` for the staged inner loop while working; `test-changed` warns when a changed source file has no matching test, and that warning is a gap to fill, not noise. Verify the change works end to end, run the full regression gate (`make test-full`) before committing, commit with `<type>(<scope>): <description>`, set the item's Status to `Done (YYYY-MM-DD)` in the table, delete the task journal in the final commit (its durable record is the Done note and the changelog; a journal left behind means the task is unfinished), and push. Final reported regression results must correspond to the final working-tree state; any modification after the final regression invalidates that result and requires the applicable gate to be rerun. Committing and pushing verified work is the default and needs no per-task approval; only destructive or history-rewriting git operations require asking first. This machine runs multiple agent sessions against the same clone concurrently, so `git status`/`git log` immediately before pushing may show commits this session did not make (e.g. `main` moved ahead while you worked). Do not force-clean or revert them — inspect the diff, and if it looks like ordinary in-progress work (not a secret, not a destructive change), push it along with your own commit rather than discarding it. **`git add` with multiple pathspecs is all-or-nothing:** if any one pathspec fails to match (e.g. a file already deleted by an earlier `git rm`), the whole command aborts with `fatal: pathspec ... did not match any files` and stages nothing at all, silently — the other, valid paths in the same invocation do not get staged either. Always run `git diff --cached --stat` right before `git commit` and confirm it lists every file the task actually touched; a commit that looks complete from `git status`'s working-tree view can still be missing files if the staging step partially failed (hit live on 2026-07-19: item 27's first commit shipped without its own `.gitignore`/test/backlog edits, caught only by a post-push `git diff` against `HEAD` and fixed with an immediate follow-up commit).

## Ranked Backlog (best ROI first)

Pending rows are ranked by a diminishing-returns score, recomputed at every groom (see `.agents/prompts/groom_backlogs.md`):

**Score = (Value × Decay) ÷ Effort**

- **Value (1–8):** pain or risk removed if the item ships.
- **Decay:** geometric halving per already-shipped item in the same theme (1.0 → 0.5 → 0.25 …) — the second polish pass on a theme is worth roughly half the first. New-capability items that open a new curve (e.g. #23, #24) always keep Decay 1.0; diminishing returns applies to polish, not to new ground.
- **Effort (1–8):** roughly log-scale; 1 = minutes, 8 = weeks.
- **ROI floor = 0.5:** items scoring below the floor stay open but are flagged ⚠️ and must not be worked without explicit user confirmation. At selection time the default is to skip past them to the highest-scoring above-floor item and ask the user whether to confirm, re-scope (shrink until it clears the floor), or close the flagged item.

Scores apply to Pending rows only; Done, Closed, and Merged rows show `—`.

### 56. Operational Resilience: Crash Recovery, Durable Resume, Repository Locking, Cancellation, and Exactly-Once Execution
Make HowlPlane operationally trustworthy under process interruption, session/laptop crashes, killed implementation or reviewer processes, repeated resume/approve commands, concurrent task runs targeting the same repository, duplicate execution attempts, Ctrl+C / cancellation, stale repository state, and partially-written artifacts.

**Governing Invariant:**
No interruption may silently lose task history, repeat consequential execution, overwrite another task's work, trust partial/corrupt artifacts, bypass review or verification, or incorrectly transition to COMPLETE.

**Scope:**
- **Durable Orchestration Checkpoints:** Explicit `interrupted` and `cancelled` states, stage checkpoints with repository fingerprints, artifact hashes, and process identity.
- **Crash Recovery:** `ai resume <task-id>` inspects durable artifacts, reconciles repository deltas for interrupted implementations without duplicate blind reruns, preserves completed reviewer work and reruns only incomplete reviewers, and resumes verification.
- **Safe-Retry Classification:** Deterministic classification (`SAFE_TO_RETRY`, `RECONCILE_FIRST`, `NEVER_AUTO_RETRY`, `ALREADY_COMPLETE`, `HUMAN_DECISION_REQUIRED`).
- **Repository Mutation Lock:** Local filesystem lock (`.git/howlplane.lock` / `.task_runs/.repo.lock`) with PID and process identity validation to prevent concurrent mutation workflows.
- **Task-Run Lock:** Atomic lock on `.task_runs/<task_id>/.task.lock` protecting lifecycle commands (`approve`, `reject`, `resume`, `cancel`, `execute`).

### 67. Narrow the agent builder TypeError shim and cover the timeout contract
`SubprocessAgentBackend.build_command` in `src/control_plane/agent_execution.py` calls `self._builder(task, cwd, role, prompt, timeout_seconds=...)` inside a bare `try`, falling back to the four-positional-argument form on any `TypeError`. `GeminiCLIBackend` and `DevinCLIBackend` still use four-argument builders, so every `build_command` call on them raises and swallows a `TypeError` as normal control flow. Worse, a `TypeError` raised *inside* any builder — including one registered by a caller through `AgentBackendRegistry` — causes a silent second invocation and then surfaces a misleading error from the retry rather than the original fault. Replace the shim with an `inspect.signature` check for a `timeout_seconds` parameter and update the `cmd_builder` annotation at line 353, which still reads `Callable[[TaskSpec, Path, str, str], List[str]]`. Also add a test that `execute()` propagates its own `timeout_seconds` into the built command, rather than only testing flag construction directly. Related: the `AgyBackend --print-timeout` change that introduced this shim is a correct provider-execution fix (`agy --help` confirms the flag, default `5m0s`) but arrived with no backlog row and no mention in the milestone's audit record. Found during the independent review of the milestone, 2026-09-02.

### 68. Root-cause the unstable collected test count
During the independent review of the Continuous Test Governance milestone, the first full run on a cold tree executed 1287 tests; every collection and run afterwards reported 1290, stably. Something the suite itself creates during a run adds three collectible tests. This is mild but it makes `--cov-fail-under` and the claim that "full pytest semantics remain intact" slightly non-deterministic, and a first-run-versus-second-run discrepancy is precisely the class of drift that a clean CI machine hits and a warm development machine never does. Identify what is being written and either make the collection independent of it or make the artifact a tracked fixture. Found 2026-09-02.

### 69. Untrack the .coverage artifact
`.coverage` appears at `.gitignore:40`, but the file was committed before that entry existed and `.gitignore` does not apply to already-tracked files. The result is that every `make coverage-python` or `make test-coverage` run leaves a modified binary artifact in the working tree. Two concrete consequences observed on 2026-09-02: `git status` is never clean after a coverage run, so a genuine unstaged change is easy to miss when staging; and `scripts/select_relevant_tests.py` reports `Conservative fallback: yes (uncertain impact: .coverage)` instead of naming the real trigger (`Makefile`, `tests/conftest.py`, or `.github/workflows/`), which undercuts the selector's explainability. Fix with `git rm --cached .coverage`. This is the fifth instance of the tracked-artifact-hygiene theme (items 2, 3, 35, 47), but unlike item 47 it has a concrete, reproducible recurrence. While here, consider having the selector prefer a `full_suite_trigger` path over an "uncertain impact" path when reporting its reason, since the trigger is the more informative explanation. Found during the independent review of the Continuous Test Governance milestone, 2026-09-02.
