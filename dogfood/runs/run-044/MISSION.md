Today relnotes only reads commit subjects from a text file that people produce by hand with `git log`. That step keeps going wrong (wrong range, merge commits included, missing commits), so we want relnotes to read the history straight from a git repository.

1. New input mode: `relnotes --repo PATH --from REF [--to REF] --version VERSION`. It lists the commits reachable from `--to` (default `HEAD`) but not from `--from`, the same set as `git log FROM..TO`, oldest first, and renders them like file input. `--from` is required in this mode. `--input` and `--repo` cannot be combined (usage error), and exactly one of them is required.
2. Merge commits are skipped. Each entry gets the commit's 7-character short hash in parentheses at the end, e.g. `- handle tabs (1a2b3c4)`. File input stays exactly as it is now, without hashes.
3. Breaking changes: a commit whose type ends with `!` (e.g. `feat!: drop node 18`) or whose message body has a line starting with `BREAKING CHANGE:` is listed in a new first section, "Breaking changes", instead of its normal section. Apply the `!` rule to file input as well, which only has subjects.
4. Errors exit with code 2 and a one-line message on stderr: a path that is not a git repository, a `--from` or `--to` ref that does not exist (name the ref in the message), and git not being installed. A valid range with no commits prints the usual `No changes.` and exits 0.
5. Commit subjects and bodies can contain any characters, including `|`, tabs, quotes and non-ASCII text; none of that may break parsing. Do not run git through a shell.

Add integration tests that create real temporary git repositories (with their own committer identity and dates, so they do not depend on the machine's git config) and cover: a normal range, the default `--to`, merge commits, both breaking-change forms, the errors in point 4, an empty range, and an awkward subject. Keep the existing tests passing unchanged. Update the README with the new mode, the section order and the error cases. `npm test` must pass.
